How one purchase flows

  1. 1

    Click Buy

    Your page asks your server to start a checkout.

  2. 2

    Make a session

    Your server tells Stripe: one dress, $2. Stripe replies with a URL.

  3. 3

    Pay on Stripe’s page

    The customer types the card there.

  4. 4

    Stripe tells your server

    A signed message called a webhook says the payment went through.

Meanwhile, the customer’s browser gets sent back to /success. That’s a different road, and it carries no proof of payment.

What if the shopper is an AI?

Checkout assumes a person with a browser. Agent shopping needs a different handshake.

Our shop speaks this too: /.well-known/ucp is its menu, and npm run agent buys the dress with a Shared Payment Token. The order still only counts when the webhook says so.

ACP
Stripe and OpenAI’s open standard. It’s what lets you buy inside ChatGPT.
UCP
Google’s open standard, built with Shopify, Walmart, Target and others. Shops publish a menu for agents at /.well-known/ucp.
Shared Payment Token
A permission slip. The agent can pay one seller, up to one amount, for a short time, and never sees your card.

Slide 9 of 13, about 60 seconds

  • Be upfront: we didn’t build this part. It’s where things are heading.
  • ACP came from Stripe and OpenAI (powers Instant Checkout in ChatGPT). UCP is Google’s open standard with big retailers.
  • Shared Payment Token: scoped to a seller, an amount, and a time window, so the agent never holds your card number.
  • Stablecoin: a crypto token pegged to $1. Only mention it in one sentence.
  • Related: the WebMCP workshop on Nov 2 covers agents using your site.
  • Optional, only if a terminal is already open: run npm run agent, show it buy the dress, and point at the front row.

The gotcha: every real webhook was rejected

What Stripe told us

No signatures found matching the expected signature for payload. Are you passing the raw request body you received from Stripe?

Our body was raw. The message sent us looking in the wrong place.

What it really was

# .dev.vars
STRIPE_WEBHOOK_SECRET=whsec_...
# pasted in AFTER wrangler dev started

wrangler dev reads .dev.vars only at startup. Fix: restart it after every change. And stripe listen and your deployed endpoint each have their own whsec_.

Slide 12 of 14, about 40 seconds

  • Tell it as a story: a perfect test payment, then every real webhook rejected.
  • Stripe’s error points at the raw body. Ours was raw. The real cause was a stale secret, because wrangler dev only reads .dev.vars when it starts.
  • Fix: restart wrangler dev after changing .dev.vars. Each whsec_ belongs to one place (the CLI listener or a deployed endpoint).

When to reach for Checkout, and when not to

Reach for it when

You need money this week. No card number touches your server, because Stripe’s page holds the form.

You want the extras for free. Receipts, Apple and Google Pay, 3-D Secure, fraud checks, test cards.

Your order is simple. One cart, one payment, then fulfill when the webhook arrives.

Skip it when

You need checkout inside your own page. Use Stripe Elements: more work, more control.

You pay other sellers. A marketplace is Stripe Connect, a different product.

You sell digital goods in an iOS app. Apple’s in-app purchase rules apply.
